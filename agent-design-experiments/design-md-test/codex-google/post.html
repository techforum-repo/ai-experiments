Retries Aren't Idempotent By Accident

A retry repeats delivery; an idempotency contract preserves the identity and outcome of the work.

A client submits an order. The server commits it, but the response disappears behind a broken connection. The client sees a timeout: evidence that it lacks an answer, not evidence that the order failed. Retrying an ordinary POST can create another order. Exponential backoff changes when that happens; it does nothing to change what happens.

Idempotency makes repeated requests converge on one intended effect. For an operation that creates something, that property needs a protocol: the client names its intent, and the server remembers what that intent produced. “Retry and hope” supplies neither identity nor memory.

01 / Identity

Name the intent before sending

Generate a random operation key before the first attempt and persist it with the pending client operation. Every retry, including one after a client restart, sends that same key. A second intentional purchase gets a new key, even when its basket is identical. A hash of the payload alone cannot distinguish those two purchases; AWS explains this distinction in its discussion of caller-provided request identifiers.

Scope the server record to the authenticated tenant, operation, and key. Store a fingerprint of validated, normalized parameters alongside it. Reusing the key with a different quantity should produce a conflict, not silently return an unrelated order. Authentication still runs on every attempt; possession of a key never grants access to somebody else’s result.

The key identifies one business intention, not one network attempt.

02 / Atomicity

Make the record and effect indivisible

A cache lookup followed by processing leaves a race: two workers can both observe an absent key. A durable unique constraint must arbitrate ownership. In this database-only example, the claim, order insert, and saved response share one transaction. PostgreSQL’s ON CONFLICT mechanism supplies the competing-insert behavior.

A crash before commit rolls everything back. A crash after commit leaves both the order and its replayable response intact. A concurrent duplicate waits on the unique constraint, then reads the committed record. Bound that wait; if it expires, return a documented retryable outcome rather than starting the work again.

An external payment call cannot join this local transaction. Commit an outbox task with the order, then deliver it using a stable downstream idempotency key. The receiver must enforce its own deduplication contract.
03 / Boundaries

Specify when the promise ends

Retention is part of correctness. Once a record expires, a late retry can become new work. Choose a retention window that covers client retries, queued redelivery, and operational recovery. Longer-lived business constraints may still be necessary: a unique merchant order reference can prevent duplication after the request ledger has been pruned.

Write the remaining behavior into the API contract:

  1. Replay policy. Define which status codes and response fields are stored. Stripe, for example, replays stored results including server errors; your policy must be equally explicit.
  2. Retry budget. Use bounded backoff with jitter for transient failures. A parameter conflict requires correction, not another automatic attempt.
  3. Recovery evidence. Log the operation key, attempt identifier, and committed resource identifier separately. Operators need to distinguish repeated delivery from repeated effects.

Test the lost-response boundary deliberately: commit, drop the connection, and resend the original key. Also race two identical requests and reuse a key with changed input. Those tests establish the promise that a happy-path retry cannot.

Keep the intention stable

  • Name the work once.
  • Commit its effect and memory together.
  • Retry within an explicit contract.
