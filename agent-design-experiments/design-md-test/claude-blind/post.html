Retries Aren't Idempotent By Accident

A retry only makes a request safer if the server has been taught to recognize it as a repeat. Without a deliberately designed idempotency key, "retry and hope" is just a slower way to double-charge your customers.

AI Field notes on request semantics, network failure, and why "just add a retry" is the sentence that precedes most duplicate-payment incidents.

Every distributed system eventually grows a retry loop. A request times out, the client shrugs, and sends it again. This works beautifully for reads — asking twice for the same account balance is harmless. It works terribly for writes. If the first "charge $40" request actually succeeded on the server but the response never made it back to the client, the client has no way to know that. From its point of view, the request simply vanished. So it does the reasonable thing and retries — and now the customer has been charged twice.

The instinctive fix is to reach for HTTP's own vocabulary: PUT and DELETE are supposed to be idempotent, meaning repeating them produces the same end state as doing them once. But idempotency is a property of how a server handles a request, not a property that a verb grants for free. A PUT /accounts/42/balance that runs balance = balance - 40 is idempotent in name and dangerous in practice. Real idempotency has to be built, and the tool for building it is the idempotency key.

01Why "just retry" fails at the worst moment

The core problem is that a network timeout is ambiguous. When a client doesn't get a response, there are at least three possible histories: the request never reached the server, the request reached the server but failed before doing anything, or the request reached the server, succeeded, and only the response got lost on the way back. A naive retry treats all three as the same case and just fires the request again. The first two histories make that safe. The third does not — and the client has no way to distinguish it from the outside.

This is why retries are most dangerous exactly where they're most tempting: payments, order placement, provisioning, anything with a side effect that costs money or resources. The system that "just retries on timeout" will work fine in testing, where failures are rare and clean, and will misbehave in production, where failures cluster around the exact moments — partial outages, packet loss, overloaded downstreams — when a duplicate write does the most damage.

02Designing the key, not just adding one

An idempotency key turns an ambiguous retry into an unambiguous one. The client generates a unique token — a UUID is fine — for each logical operation, not for each HTTP attempt, and sends it as a header. The server's job is to remember, for some retention window, which keys it has already seen and what it did about them. On a repeat, it doesn't reprocess; it returns the stored outcome.

payments_api.py
# POST /charges  — client sends Idempotency-Key header once per logical attempt
@app.route("/charges", methods=["POST"])
def create_charge(request):
    key = request.headers.get("Idempotency-Key")
    if not key:
        return error(400, "Idempotency-Key required")

    with db.transaction():
        # Unique constraint on `key` makes this check-then-act atomic:
        # a concurrent duplicate insert fails instead of racing past us.
        existing = db.execute(
            "SELECT status, response_body FROM idempotency_keys "
            "WHERE key = %s FOR UPDATE", key
        )

        if existing:
            if existing.status == "in_progress":
                return error(409, "Request with this key is still processing")
            # Same key, already resolved — replay the stored result, do nothing new.
            return respond(existing.response_body, status=existing.status)

        db.execute(
            "INSERT INTO idempotency_keys (key, status) VALUES (%s, 'in_progress')",
            key
        )

    # Only reached on a genuinely new key.
    result = charge_card(request.body.amount, request.body.card_token)

    db.execute(
        "UPDATE idempotency_keys SET status = %s, response_body = %s WHERE key = %s",
        "completed", result.to_json(), key
    )
    return respond(result, status=201)

Three details separate a working implementation from a decorative one. First, the check-and-reserve step must be atomic with respect to concurrent requests carrying the same key — hence the row lock and the unique constraint, so two retries arriving at once can't both slip past the check and both call charge_card. Second, the key must scope to the operation, not the client or session; a UUID generated fresh per "attempt to place order #8891" and reused across retries of that exact attempt, never across two different orders. Third, stored keys need a retention window and, ideally, a hash of the request body — so a key reused with different parameters is rejected rather than silently replayed with stale data.

Edge case worth naming: what if the retry arrives while the first attempt is still mid-flight, not yet lost, just slow? This is why the handler above returns 409 for an in_progress key rather than blocking indefinitely or, worse, letting a second worker start a second charge. The client should back off and poll or retry again shortly — the key guarantees at-most-once execution, not instant confirmation.

None of this requires exotic infrastructure. A single table with a unique key column and a status enum is enough to convert a large class of double-processing bugs into a non-issue. What it does require is treating idempotency as a contract between client and server that's specified up front — which fields form the key, how long results are retained, what happens on a concurrent collision — rather than a property you hope emerges from calling the right HTTP verb.

Takeaway

Idempotency isn't a side effect of retrying carefully — it's a mechanism you build, keyed on the operation, checked atomically, and honored on every replay. Design the key before you design the retry.
