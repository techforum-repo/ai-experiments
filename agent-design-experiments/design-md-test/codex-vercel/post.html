Retries Aren't Idempotent By Accident

A retry becomes safe when the server can recognize the original intent and recover its result across failures.

2 attempts
1 operation key
1 committed effect
3 boundaries: identity, commit, retention

A client submits an order. The server commits it, then the connection drops before the response arrives. The client sees a timeout; the database sees success. Retrying is a reasonable recovery action, but another ordinary POST can create another order. Backoff changes when that happens. It does nothing to establish whether the operation already happened.

A timeout is missing knowledge, not evidence of a missing effect.

The useful guarantee is narrow: repeating the same logical operation must not repeat its business effect. Delivering that guarantee requires a protocol spanning the caller, the handler, and durable storage. A header named Idempotency-Key is only the identifier carried by that protocol.

01 / Name the intent

Generate a random key when the user initiates an operation, persist it with the pending work, and reuse it for every attempt. Generating a new key inside the retry loop gives every duplicate a fresh identity. Conversely, hashing only the request body can collapse two intentional purchases of identical items. Caller-provided identifiers distinguish those intentions, a distinction described in the Amazon Builders’ Library.

Scope the stored key to the authenticated tenant and operation. Bind it to a fingerprint of validated, canonical request parameters. If the same scoped key arrives with different parameters, reject it as a conflict. Never silently replay an unrelated result. Authentication and authorization still apply to every attempt; possessing a key grants no access.

02 / Make recognition atomic

A lookup followed by an insert is insufficient: concurrent requests can both observe an absent key. Enforce uniqueness on the scoped key in the database. PostgreSQL’s INSERT documentation describes conflict handling against unique constraints. The handler below uses a transactional claim built on that constraint, rather than an in-memory check.

Commit the key record, order, and replayable response in one transaction. A crash before commit leaves none of them; a crash afterward leaves enough information to answer the retry. Store the response status and body, plus any application headers needed for replay. Bound contention waits and return a documented retryable outcome when another attempt still owns the transaction.

This boundary covers local database effects. An external payment cannot join that transaction merely because the handler calls it. Persist an outbox entry with the order, then deliver it using a stable downstream idempotency key. The receiver must enforce deduplication too; an outbox alone permits duplicate delivery.

03 / Define when memory ends

Deduplication lasts only as long as its evidence. Publish a retention window that covers supported retries, delayed queue deliveries, and recovery jobs. After deletion, the same key can look new. For irreversible operations, keep a durable business identifier or require reconciliation after the window expires instead of blindly resubmitting.

Test the uncertain outcomes directly: drop the response after commit, race identical requests, change parameters under one key, and replay after expiration. Verify the number of business effects as well as the responses. Successful HTTP requests alone cannot prove this contract. Record duplicate hits, parameter conflicts, and claim wait times so production behavior exposes broken assumptions. A sudden drop in duplicate hits can mean callers have started regenerating keys, even while their retry success rate looks healthy.

Design the identity before enabling the retry.

  • Keep one key for one intent.
  • Commit the effect and its evidence together.
  • Make the retention boundary explicit.
