Retries Aren't Idempotent By Accident

A network timeout tells you nothing about whether the request it was waiting on actually succeeded — which means every retry is a bet, and the idempotency key is the only thing that makes the bet safe.

When "At Least Once" Means "At Least Twice"

Every retry strategy is built on an assumption most engineers never say out loud: that sending the same request twice is safe. It usually isn't. A client library times out waiting for a response from the payments service, retries with backoff, and gets a 200 back — except the first request had already succeeded on the server, and the customer is now charged twice. The server had no way to know the second POST was a retry of the first. It looked like a brand-new request, because as far as HTTP is concerned, that's exactly what it was.

A retry is only as idempotent as the key you gave it — everything else is optimistic accounting.

This is the gap between transport-level reliability and business-logic correctness. TCP, and the retry logic most people build on top of it, guarantee that bytes eventually arrive — that's "at least once" delivery. They say nothing about whether the client ever learns the outcome. A dropped response, a load balancer that recycles a connection mid-flight, a Lambda that gets frozen and retried by the platform — all of these produce the exact same symptom from the client's point of view: silence. And silence is indistinguishable from "still processing," "failed before doing anything," and "succeeded but the response got lost." Treating all three as "just retry" is how idempotency bugs get into production.

Designing the Key, Not Just Checking It

An idempotency key isn't a nonce you bolt onto a request as an afterthought — it's a statement of intent from the client: "this is one logical operation, no matter how many times you see it." That statement only works if three things are true. First, the key is generated once per logical operation, client-side, before the first attempt — never regenerated on retry. Second, the server persists the key and the outcome atomically with the side effect it's protecting, not in a separate step that can itself fail halfway. Third, a request that arrives while the original is still in flight gets rejected or queued, not processed a second time in parallel — the classic gap that a naive "check, then act" pattern leaves wide open.

That last point is the one most implementations get wrong. Checking whether a key exists and then inserting a record are two operations; if two retries race between them, both can pass the check. The fix is to make the claim on the key atomic — typically a unique constraint on the idempotency key column, so the second insert fails fast and the handler can treat that failure as "someone's already working on this."

server.tsPOST /charges
app.post('/charges', async (req, res) => {
  const key = req.header('Idempotency-Key');
  if (!key) return res.status(400).json({ error: 'missing key' });

  // Atomic claim: unique constraint on (account_id, key) does the
  // real work here. A duplicate insert throws, it doesn't race.
  const claim = await db.query(
    `insert into idempotency_keys (account_id, key, status)
     values ($1, $2, 'in_progress')
     on conflict (account_id, key) do nothing
     returning id`,
    [req.account.id, key]
  );

  if (claim.rowCount === 0) {
    const prior = await db.query(
      `select status, response from idempotency_keys
       where account_id = $1 and key = $2`,
      [req.account.id, key]
    );
    if (prior.rows[0].status === 'in_progress') {
      return res.status(409).json({ error: 'request already in flight' });
    }
    return res.status(200).json(prior.rows[0].response); // replay
  }

  const result = await chargeCard(req.body);
  await db.query(
    `update idempotency_keys set status = 'done', response = $1
     where account_id = $2 and key = $3`,
    [result, req.account.id, key]
  );
  res.status(200).json(result);
});
The unique constraint on (account_id, key) is what actually prevents the double charge — the lookup logic around it is just there to answer politely.

Caveat

Scope the key to the account and the operation, not just a raw string the client picks. A key that's globally unique but not tied to account_id lets one tenant's retry collide with another's request by coincidence — rare, but not rare enough to ignore in a multi-tenant system.

The retry logic decides when to try again. The idempotency key is the only thing that decides whether trying again is safe — design it with the same care you'd give the operation it's protecting.

  • At-least-once delivery is a transport guarantee, not a business-logic guarantee
  • The key belongs to the client's intent — generated once, reused on every attempt
  • Claim the key atomically before doing the work, not after finishing it
  • A lost response and a failed request look identical to the client — the key is what tells them apart
