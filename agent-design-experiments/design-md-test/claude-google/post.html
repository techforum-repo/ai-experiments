Retries Aren't Idempotent By Accident

A timeout can't tell a client whether the server never saw the request, finished it and lost the reply, or crashed halfway through. Retrying blindly treats all three the same — the fix is a key the server was built to recognize, not a loop that hopes for the best.

A request leaves the client. Somewhere between there and the server, the connection stalls, and the client's only observation is a timeout — no confirmation, no error it can fully trust, just silence where a response should have been. The reasonable-sounding move is to retry. Most HTTP clients, SDK wrappers, and service meshes will do exactly that automatically, on the theory that trying again is strictly safer than giving up.

It isn't, not by itself. A timeout doesn't tell you what happened on the other end — only that you stopped hearing about it. The request might never have reached the server. It might have been received, processed, and fully committed, with only the acknowledgment lost on the way back. It might have been half-processed when the server itself crashed. All three look identical from the client's chair, and "retry and hope" responds to them as if they were the same problem. For a request that charges a card, books a seat, or sends an email, that's how a single blip becomes two.

An idempotent retry isn't a retry that happened not to change anything.
It's a retry the server was built to recognize.

The Timeout Doesn't Tell You What Happened three outcomes, one signal

Every call that doesn't return cleanly collapses onto the same observable at the client: no response, or an error it can't fully trust. Underneath that single signal sit at least three distinct server-side outcomes, and they call for opposite responses. The request may have died before it arrived, in which case retrying is exactly correct — nothing happened yet. The server may have received and fully committed the write, with only the response lost on the way back, in which case retrying without protection reprocesses a request that already succeeded. Or the server may have started the work and failed partway through — a payment authorized but the order row never written — leaving a state a naive retry can't safely resume and a naive skip can't safely ignore.

This is a practical instance of the two generals problem: no protocol over an unreliable network can guarantee both sides agree a message was received, because the acknowledgment itself can be lost the same way the original message can. You can't fix this by trying harder to deliver the response. What you can fix is what happens when the same logical request arrives at the server twice — which is the only lever a retry actually gives you.

The Idempotency Key Pattern check before you act, not after

The fix is a token the client generates once per logical operation — not once per HTTP attempt — and attaches to every retry of that same operation, typically as an Idempotency-Key header. The server's job is to treat that key, not the request body, as the real unit of work: before running anything with side effects, it checks whether the key has been seen before. Internally, a key's record moves through three states — pending reserved but not yet started, in_flight a worker is actively running the handler, completed the response is cached and ready to replay — and only a key that has genuinely never been seen is allowed to trigger the underlying business logic.

FIG. 01 — IDEMPOTENT POST HANDLERPSEUDOCODE · PYTHON-STYLE
@app.post("/charges")
def create_charge():
    key = request.headers.get("Idempotency-Key")
    if not key:
        abort(400, "Idempotency-Key header is required")

    existing = idempotency_store.get(key, scope=current_account.id)

    if existing is None:
        # First time we've seen this key — reserve it atomically
        # before doing anything with side effects.
        reserved = idempotency_store.reserve(
            key, scope=current_account.id, request_hash=hash_body(request)
        )
        if not reserved:
            # Lost a race with a concurrent duplicate attempt.
            abort(409, "Request with this key is already in flight")
    elif existing.request_hash != hash_body(request):
        abort(422, "Key reused with a different request body")
    elif existing.status == "completed":
        return existing.response, existing.status_code
    elif existing.status == "in_flight":
        abort(409, "Request with this key is already in flight")

    charge = payment_gateway.charge(request.json)   # the actual side effect
    idempotency_store.complete(key, current_account.id, charge.to_json(), 201)
    return charge.to_json(), 201
reserve() has to be a single atomic operation — a unique constraint on (account_id, key), not a check followed by a separate insert — or two concurrent retries can both pass the check before either has finished writing.
  1. Scope the keyPair it with the account or tenant, not a global namespace — two different customers reusing the same client-generated UUID shouldn't collide.
  2. Fingerprint the requestStore a hash of the body alongside the key, and reject a retry that reuses the key with a materially different payload instead of silently serving the wrong cached result.
  3. Reserve before you actThe row that claims the key has to exist before the side effect starts, in the same transaction or a preceding one — never as an afterthought written once the charge already went through.
  4. Expire it after a bounded window24 hours is a common default: long enough to outlive a realistic retry storm, short enough that the store doesn't grow forever.

What The Retry Actually Looks Like same key, two attempts

Trace one logical charge across an attempt that times out and a retry that succeeds, and the value of the key becomes concrete: the server never runs the handler twice, no matter how many times the client asks.

Also worth knowing

HTTP already has a notion of idempotent methods — GET, PUT, and DELETE are specified as safe to repeat, because a correctly implemented server produces the same end state regardless of how many identical requests arrive. That guarantee is structural to those methods; POST gets no such promise from the spec; it's defined as neither safe nor idempotent, because a POST typically creates something new each time it's called. An idempotency key is what gives a POST the property PUT gets for free — deliberately, at the application layer, not as a side effect of the HTTP verb.

A retry without a designed idempotency key isn't resilience — it's a bet that duplication won't matter, running until it does.

  • A timeout tells the client nothing about what the server did.
  • Idempotency is a contract the server enforces, not a side effect of a retry loop.
  • The key is scoped, fingerprinted, and reserved atomically before the write.
  • GET is idempotent by accident; POST only by design.
